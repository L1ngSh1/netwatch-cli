## 1. 核心判断

项目继续只回答三个问题：**连在哪、流量从哪里出去、当前路径表现怎样。**

下一步不是继续拆目录，而是：**先统一重复判断和错误语义，补齐安装验收，再验证真正影响安装体积的候选。** 不增加后端、插件系统、依赖注入容器、诊断服务层或配置迁移。

当前还有局部规则重复，但原来最明显的入口反向依赖已消除。把文件变短、把函数搬家、增加抽象层，均不单独算成果。

## 4. 分步任务与验收点

### N1-A：先修“失败结果仍给成功诊断”——首个实施补丁

**问题证据**：`netwatch/speedtest/analysis.py:44–78` 的置信度没有统一检查 error、空结果和非法数值；`netwatch/cli_modules/speedtest.py:143–157` 的表格报错返回后，外层仍可继续打印详细诊断。

**最小补丁**：在现有诊断层集中判断结果是否可分析，展示层消费该判断。先用测试固定语义，再修改 helper 和显示 guard；不改 parser、测速执行、结果持久化或冻结函数。

**验收**：

- error、完全无测量、NaN、正负无穷、负值、越界丢包率不产生成功质量结论。
- 0 仍是合法数值；“缺可选指标”“测量异常”“测速失败”分开表达，不把缺 jitter/loss 自动当作后端失败。
- 部分有效测量、仅接口事实仍可按证据展示；已有正常 HIGH/MEDIUM/LOW 用例语义保留。未知状态的展示名称先在契约中明确，不默默改公共返回值。
- 失败表格后不追加成功诊断；主菜单 5 与高级 1 的原简洁/详情行为不变。
- 新用例先 RED 再 GREEN，完整套件通过，两个冻结函数 AST 和行为检查通过。

**回退**：诊断 helper、显示 guard、新测试同一小补丁回退。完成后停止，先评审再进入 N1-B。

### N1-B：让各处网络路径判断使用同一份事实

**问题证据**：`analysis.py:103–114` 与 `runner.py:287–302` 分别判断 VPN；后者把普通 virtual 接口也用于 VPN 警告。前缀判断只覆盖 `198.18.*`；CLI `speedtest.py:294–300` 又把未检出 VPN 倾向解释成直连。

**最小补丁**：复用平台分类，集中一个小型路径证据 helper；详情、摘要和简洁判断都消费它，不新造规则框架。区分 VPN/TUN 线索、普通虚拟接口、其他/未知；地址判断使用合法网段解析而非字符串前缀。

**验收**：utun/Wintun、bridge、物理接口、完整 `198.18.0.0/15` 及相邻网段、非法地址、缺 raw 都有合成用例；相同输入的各处结论一致。普通 bridge 不等于代理；基准测试地址只作为线索，不单独证明实际流量经过 VPN；未检出 VPN 不等于证实直连。一般 virtual 是否影响置信度须先明确，不能让实现顺便改变正常评级。

**回退**：判定 helper、消费者接线与对应测试一起回退；不改网卡发现、路由查询和后端执行。

### N1-C：诚实的等待提示——可独立验收的小补丁

**问题证据**：`netwatch/cli_modules/speedtest.py:53–58,131–137` 会在 `task()` 前打印下载/上传阶段。

**最小补丁**：只保留可确认的“执行中/等待结果”提示；不引入线程、进度事件框架或新后端协议。

**验收**：mock 事件顺序为进入等待 → 调用后端 → 后端返回 → 结束等待；没有虚构阶段，结果返回与 Ctrl+C 行为不变。该项与 N1-A/B 分开提交和回退。

### N2：补强 P6 的数据验收，不重做打包系统

**问题证据**：`scripts/dev/verify_wheel.py:24,39` 检查文件存在并输出 SHA，却不对照固定真值；`verify_installed.py:45–48` 只检查三个数据文件存在。当前源码哈希测试不等于最终 wheel 和安装内容正确。

**最小补丁**：开发验收侧保留一份经审查的固定数据真值；源码、wheel、安装检查共用。检查缺失、空/截断/替换和重复 wheel 成员；安装后执行一次真正的本地中心点查询。不增加运行时依赖或修改定位算法。

**验收**：

- 三份运行时数据逐一注入损坏均失败；正常包通过。expected 值不由待校验文件自己生成。
- 干净 wheel 安装用 `python -I` 验证模块确实来自安装环境；已安装数据查询结果和记录数符合固定真值。
- 查询安排在原冷启动断言之后，保留高级模块 `0 → 7` 延迟加载合同。
- 保留 CSV 字节/换行、依赖 metadata、entry point、已有可选能力测试及默认 I/O guard。

**回退**：仅回退验收脚本、真值和测试，产品运行时不受影响。N2 技术上独立于 N1，可并行审查，落地仍逐个验收。

### N3：浏览器安装减重实验——通过后再决定推广

**候选**：保留 Playwright 与 headless 浏览器，仅省去未使用的完整 Chromium。官方文档支持未指定 channel 的 headless shell 安装方式；这只证明方案存在，不证明本项目所有允许版本已兼容。[Playwright 官方说明](https://playwright.dev/python/docs/browsers#chromium-headless-shell)

**历史收益线索**：同一 2026-10-19 测量口径下，374.33 → 179.50 MB，估算少 194.83 MB / 约 52%；只是候选值，尚未成为当前安装行为。

**先做实验，不先改默认安装**：

1. 固定 OS/架构、Python、Playwright、wheel 及依赖版本，分别记录下载主体、包内逻辑大小、安装占用、缓存占用；冷/热缓存分开，不混用 MB 与 MiB。
2. 复核 `playwright>=1.44` 的最低兼容边界，以及 `--only-shell` 是否在全部受支持版本可用；任何版本下限调整单列评审，不只替换 README 命令。
3. 独立临时浏览器目录只装候选组件；显式本地 HTML/JS、两个入口 launch 参数、错误/取消处理验收。真实浏览器安装验收与默认 pytest 分开，默认 pytest 仍全 mock。
4. macOS、Linux、Windows 分别复验；系统库、浏览器版本和用户实际使用的能力相同才比较。旧的本地 HTML 通过不代替新平台证据，也不代替真实测速网结果。

**推广门禁**：兼容、能力和各平台安装验收通过，且收益由测量支持后，再评审独立安装补丁；同步 README、安装提示、安装检查和 CI。证据不足就保留现状，记录未通过项。

**回退**：恢复旧安装命令和配套文档/检查，必要时在新环境补装完整 Chromium；不删除用户已有浏览器缓存。不把验证码问题混入本任务。
